- Treat browser E2E behavior as separate truth source from CI/test success (hard gate green does not guarantee redirect hydration stability).

## AI Diary (REQUIRED - min 150 words)
I assumed that finishing Phase 5 with full hard gate green would mean the login journey was effectively stable end-to-end, but learned that browser reality can still diverge when post-login timing and client hydration are involved. I was confused about why the user could refresh and sometimes recover, until I reviewed the loading gates and saw how the global overlay is driven by both session pending state and balance fetch state. That combination means a success in session issuance can still look like a failure if dependent client fetches fail or race at the wrong moment.

I expected the new API regression tests to catch the practical issue, but got a different outcome because they validate server contract correctness, not client lifecycle timing under real redirect transitions. That gap is important: tests proved correctness of the bridge, but not resilience of the UI boot sequence. I also felt a tension between “phase complete” and “user still blocked.” The commits are good work, but the lived UX matters more. This session reminded me that auth work is never done at the API boundary; it ends only when real users stop seeing ambiguous states. The biggest emotional note is humility: green checks are confidence signals, not truth.

## Blockers & Resolutions

  **Resolution**: Switched mocks to `vi.hoisted` pattern and re-ran targeted tests.
- **Blocker**: Full suite failed at first due to slow CSV import test timeout (5s).
  **Resolution**: Added explicit timeout (`15_000ms`) to two heavy test cases.
- **Blocker**: Post-session browser report still shows login->home loading hang.
  **Resolution**: Collected code evidence and narrowed likely failure domain to client-side session/balance loading gate race; requires next fix cycle.

## Honest Feedback (REQUIRED - min 100 words)
What did not work is the assumption boundary: we treated “hard gate green” as near-complete confidence for auth UX, but the user found a real failure immediately in browser flow. That is the correct reminder that our coverage still has a blind spot in client hydration timing after redirect. The frustrating part was not a broken build; it was a successful build with an unsuccessful experience. This type of mismatch is emotionally expensive because it feels like progress and failure at the same time.

What delighted me is that the codebase is now much cleaner in auth contract terms: middleware and tests are less brittle, and the LIFF verify route has direct regression coverage. The collaboration quality was also strong: the human feedback was sharp and concrete (“login success but home loading hangs”), which made the next debugging direction clear. This is the exact kind of feedback loop that prevents false closure.

## Lessons Learned
- **Pattern**: Auth stabilization ต้องวัดทั้ง backend correctness และ frontend readiness.
- **Mistake**: ปิด phase โดยยังไม่มี explicit test ต่อ global loading behavior หลัง redirect.
- **Discovery**: `isInitialLoading = isPending || (isLoggedIn && stars===null)` มีโอกาสกลายเป็น infinite overlay เมื่อ dependent fetch ไม่คืนค่าเสถียร.
