## 🧠 AI Diary: Implementation Insights

**What Went Well**:
1. **State Machine Design**: PaymentModal as a single orchestrator was much cleaner than separate modal wrappers. The 5-step flow (`method-select` → step 2a/2b → `receipt`) felt natural.
2. **Component Reusability**: Each component (MethodSelector, PromptPayQR, etc.) had clear responsibilities. Easy to test and compose.
3. **PCI Compliance**: Using Omise.js `createToken` client-side meant zero risk of card data touching our servers. Included security notice in CardForm.
4. **Polling Loop**: Custom countdown + auto-poll in PromptPayQR was straightforward. 10-min timeout with 4s intervals = safe for QR expiry.
5. **Hard Gate First**: Build/lint passed immediately. No surprises.

**What Was Frustrating**:
1. **JSX Nesting Error**: Missed a closing `</GlassButton>` tag when replacing Stripe → Omise. Caught on first build attempt.
2. **Modal `onClose` Type**: Initial attempt to conditionally disable close button had type issues. Simplified by letting Modal.tsx handle hideCloseButton logic.
3. **Omise.js Typing**: No `@types/omise` package exists. Had to manually declare `window.Omise` interface — but this was expected and documented.

**Learned**:
- Framer Motion's `AnimatePresence` + conditional rendering is powerful for multi-step flows.
- Keeping component files small (<200 lines) makes them easier to reason about and test.
- Zod validation in react-hook-form is clean; error messages display naturally.
- Polling logic: Storing refs (`successFiredRef`) prevents double-fires on re-renders.
